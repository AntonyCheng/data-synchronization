# 数据同步平台 PRD（v0.3）

> 本版本目标：在已确定 SeaTunnel Zeta 为同步执行引擎、RuoYi-Vue-Plus 为管理平台底座的前提下，明确 MVP 的同步语义、安全边界、异常恢复和验收口径。
> v0.3 更新：明确 MySQL binlog CDC 属于 MVP；修正 checkpoint 归属；补充任务生命周期、目标端写入语义、CDC 前置检查、表结构变更、数据核对与验收要求；统一技术架构和阶段范围。

---

## 一、背景与问题

- 此前已经在直接基于 Apache SeaTunnel 做落地验证（MySQL/GoldenDB → Kafka），但发现在还没想清楚整体需求边界的情况下直接抠某个引擎的实现细节，容易"只见树木不见森林"。
- 因此退一步，先明确产品要解决的问题、覆盖的场景和功能范围，再回头评估 SeaTunnel（或 DataX / Flink CDC / 自研）是否是合适的底层引擎，以及怎么用。

## 二、目标（本阶段）

做一个**面向企业内部使用的数据同步管理平台**，第一阶段聚焦：

- **源端**：仅 MySQL（短期不考虑其他源数据库）
- **目标端**：MVP 首先完整支持 PostgreSQL，跑通 MySQL → PostgreSQL 的全量、增量及全量+增量闭环；Oracle、SQL Server 等关系型目标按优先级扩展，Kafka、Redis、MongoDB、Elasticsearch 等非关系型目标在后续阶段实现
- 提供统一的**任务配置、执行调度、监控告警**能力，而不是让使用者直接写同步引擎的配置文件
- 定位：**纯数据复制平台**，允许选择表和排除非同步键字段，但不提供计算字段、聚合、关联、行过滤等数据加工能力；任务之间互相独立、无依赖关系

## 三、参考对象说明

调研了几类现有产品，各自定位不同，可以分别借鉴：

| 类型 | 代表产品 | 值得借鉴的点 |
|---|---|---|
| 开源同步引擎 | DataX | 插件化架构（Reader/Writer 解耦）思路简单清晰，适合离线全量场景 |
| 开源集成引擎 | Apache SeaTunnel | 连接器生态丰富（100+ 数据源），支持全量/增量自动切换、分布式、断点续传 |
| 开源 CDC 引擎 | Flink CDC / Debezium / Canal | 基于 binlog 的增量捕获能力强，一致性保障好，但部署依赖较重 |
| 商业化数据集成平台 | 阿里云 DTS、腾讯云 WeData、FineDataLink 等 | **产品化的功能模块划分**——数据源管理、任务编排、元数据/血缘、数据质量监控、告警——这部分对我们设计"平台"而不是"脚本工具"更有参考价值 |

其中 DataX 只支持单机、无实时能力，SeaTunnel 与 Flink CDC 支持分布式和 CDC。这个对比结论可以先记下，作为后续技术选型阶段的输入，但**不影响本阶段的需求梳理**。

## 四、功能模块拆解（建议的平台功能地图）

### 1. 数据源管理
- 数据源的注册、编辑、连接测试、凭证管理（避免明文密码散落在配置文件里）
- 按类型区分：关系型（MySQL/PG/Oracle/SQLServer）、消息队列（Kafka）、NoSQL（Redis/MongoDB/ES）
- 数据源的元数据探查：库表结构、字段类型、索引/主键信息，为后续字段映射做准备
- MVP 支持的 MySQL、PostgreSQL 具体版本范围在 Phase 0 POC 后形成正式兼容矩阵；矩阵外版本允许尝试连接，但不承诺完整兼容
- 创建 CDC 任务前执行源端预检查：`log_bin=ON`、`binlog_format=ROW`、`binlog_row_image=FULL`、复制权限、唯一 `server-id`/ID 范围、时区、连接超时和 binlog 保留策略；平台负责为同一 MySQL 集群上的并发 CDC 作业分配并保留不冲突的 `server-id`；不满足硬性条件时禁止创建任务并给出修复说明
- **类型映射策略**（三层设计，用户默认无需操心细节）：
  - 常规字段类型：内置映射表自动转换（如 MySQL `int` → PostgreSQL `integer`）
  - 有歧义的字段类型（如 `tinyint(1)` 常被当布尔值用）：平台检测后给出明确提示+推荐映射，用户确认即可，不要求理解底层原理
  - 同步到非关系型目标时采用目标端明确的标准模型：Kafka 使用包含操作类型、表名、同步键、行数据和事件时间的 JSON 事件；Redis 使用 Hash 字段映射并定义删除 key 语义；时间字段统一使用 ISO 8601 表达
  - 无法无损映射或不在兼容矩阵内的类型默认阻断任务，不允许静默降级为字符串；可选兼容策略必须明确展示精度、范围或语义损失

### 2. 同步任务管理
- 任务创建向导：选源 → **选同步粒度（整库 / 多表 / 单表）** → 选目标 → 字段映射（含类型自动转换建议）→ 同步方式选择
- **任务模型**：一个平台逻辑任务包含一个或多个表实例，并映射到一个或多个 SeaTunnel 作业；平台必须保存逻辑任务、表实例、引擎 `jobId`、配置版本之间的关系，以支持表级状态展示、新表接入和故障隔离
- **同步粒度**（三档，逐级细化）：
  - **整库同步**：选一个库，库内所有表整体同步；默认自动纳入库中新增表。平台定期扫描发现新表后，先创建独立表实例并完成连接、主键、类型等检查；有历史数据时先完成该表全量，再进入 CDC。单表接入失败不应影响已正常运行的其他表
  - **多表同步**：从库中勾选若干指定表
  - **单表同步**：只针对一张表，可排除非同步键字段；行过滤不纳入 MVP
- **同步方式**（MVP 阶段三种都要支持）：
  - **全量同步**：支持一次性全量和周期性全量；输出应对应一个明确的一致性快照水位，水位之后的变化只有“全量+增量”任务才继续同步。写入已有目标表时必须明确选择目标数据处理模式，不能默认追加
  - **增量同步**：MySQL 源端基于 binlog（ROW 模式）做 CDC。纯增量要求目标端已有可信基线；可从任务创建后的最新位点开始，也可由高级用户指定时间或 binlog 文件+位置，创建前必须提示不会自动补齐此前历史数据
  - **全量+增量**：优先使用 SeaTunnel MySQL CDC 的 `startup.mode=initial` 完成一致性快照并连续进入增量，不由平台拆成两个彼此独立的任务，避免切换窗口丢数
- **断点续传（checkpoint）机制**：
  - SeaTunnel 引擎 checkpoint/savepoint 是恢复状态的唯一权威来源，存放在引擎配置的持久化 checkpoint 存储中；单机部署也必须使用独立持久化目录并设置保留数量，不依赖临时目录
  - 平台元数据库只保存任务与引擎作业的关联、配置版本、最近成功 checkpoint 元数据、展示用 binlog/GTID 信息，不自行拼装或替代引擎 checkpoint
  - GTID 作为推荐的源端能力进行检测和展示，但不是平台唯一的恢复机制；未启用 GTID 时仍由引擎 checkpoint 保存实际 binlog 状态
  - 若任务停机时间超过 binlog 保留期，导致恢复所需日志已被清理，任务进入“需重新初始化”状态，禁止悄悄从最新位点继续
- **任务操作语义**：
  - **启动**：校验配置版本后提交新的引擎作业
  - **暂停**：触发引擎 savepoint/checkpoint 并保留恢复状态；只有保存成功后任务才进入“已暂停”
  - **恢复**：使用原任务的引擎状态和相同配置版本恢复；涉及字段映射、主键或同步范围变化时不能直接恢复
  - **停止**：终止作业，不承诺保留可恢复状态；界面需二次确认并明确与“暂停”的差别
  - **失败重试**：优先从最近成功 checkpoint 恢复，不重复执行全量
  - **重新初始化**：丢弃原恢复状态并重新执行全量，属于高风险操作，必须说明对目标数据的处理方式并二次确认
- 已发布的任务配置不可原地覆盖；修改同步范围、同步键、字段映射或目标表时生成新配置版本，并重新执行预检查。恢复操作只能使用产生该 checkpoint 的配置版本
- 平台任务状态至少包括：草稿、校验中、全量运行中、增量运行中、暂停中、已暂停、恢复中、失败可恢复、需重新初始化、已停止、已完成
- 任务之间互相独立，无依赖调度需求（纯复制场景，暂不需要"任务编排"能力）

### 3. 调度与编排
- 单任务的调度周期配置（一次性 / cron / 常驻实时）
- 全量或全量+增量写入已有目标表时，必须选择一种目标数据模式；周期性全量沿用同一规则：
  - **合并（upsert）**：更新已有主键并插入新主键，不删除目标端多余数据，适合汇集场景，不承诺与源端完全镜像
  - **覆盖刷新**：优先写入临时表并在成功后替换正式表；若目标库无法安全替换，则要求维护窗口并明确展示不可用风险。任何失败都不得留下“任务显示成功但目标只有半张表”的状态
- 同一任务禁止并发触发多个运行实例；上一次仍在运行时，新的 cron 触发默认跳过并记录原因
- 任务间无依赖调度需求（纯复制场景，暂不需要"任务编排"能力）

### 4. 监控与告警
- 任务级：运行状态、当前阶段（快照/CDC）、同步速率（条/秒和字节/秒）、增量延迟、失败重试次数、最近成功 checkpoint 时间
- 表级：各表运行状态、快照总量与完成量、最后处理事件时间、错误原因；整库/多表任务不能只展示一个汇总状态
- 数据级：全量完成时进行源目标行数核对，并按主键范围进行分块计数或校验和；持续 CDC 场景只允许在同一水位或任务暂停后做精确核对，不能直接比较两个持续变化的实时行数
- 增量延迟统一定义为“目标端成功提交时间 - 源端 binlog 事件时间”，并同时展示最近一次成功提交时间，避免任务假运行却显示低延迟
- **告警渠道：不纳入 MVP 范围**，MVP 阶段先保证监控界面能看到任务状态和异常，主动推送告警放到后续阶段做，避免 MVP 功能过重

### 5. 元数据与变更管理
- 源端表结构变更处理策略，采用**分级处理**：
  - **低风险变更**：新增可映射、允许为空或带可兼容默认值的字段。只有该目标库已进入“自动 DDL 支持矩阵”且预检查通过时才自动同步；否则暂停受影响表并提示人工处理
  - **高风险变更**：删字段、重命名字段、缩小字段长度、改类型、改主键/唯一键等。检测到后自动暂停受影响表并记录事件，等待人工确认后再继续
  - 任一表发生结构变更时，默认只隔离该表，不影响同一逻辑任务中的其他正常表；若当前引擎作业无法做到表级隔离，则整组暂停并明确列出受影响范围
- 这块在异构目标（比如同步到 Kafka）时尤其要想清楚——Kafka 没有"表结构"这个概念，需要定义好消息格式（如统一用 JSON/Avro schema）
- **同步键前置检查**：优先使用源表主键；无主键时只接受所有组成列均为 `NOT NULL` 的唯一索引。存在多个候选唯一键时由用户选择；同步键字段禁止排除或改为不兼容类型。没有可靠同步键的表禁止启用 binlog 增量，只能走全量同步

### 6. 权限与安全
- 操作人账号体系、任务归属、操作审计日志
- **数据源凭证存储**：平台内加密存储（现阶段不对接外部密钥管理系统），用于解密的主密钥必须通过部署环境或受保护配置注入，不能与密文保存在同一数据库中
- 平台生成的 SeaTunnel 配置、接口请求日志和作业日志不得输出明文密码；临时配置用后立即清理，展示日志统一脱敏
- 数据源账号权限建议区分申请：源端读账号需要 `REPLICATION SLAVE`/`REPLICATION CLIENT`（读 binlog）+ `SELECT`（全量读取），与目标端写账号（建表/增删改）权限分开管理，避免一个账号权限过大

### 7. 可视化管理界面
- 任务列表、运行监控看板、日志查看——这是把"平台"和"脚本工具"区分开的关键部分

### 8. 数据安全与冲突处理（围绕核心同步功能的补充设计）
- **关系型目标默认写入语义**：按同步键执行幂等 upsert；源端 INSERT/UPDATE 在目标端写入最新行状态，源端 DELETE 默认在目标端硬删除，以实现单向镜像。目标表默认由同步任务独占写入，不支持把目标端人工修改再合并回源端
- **目标表不存在**：平台自动建表。MVP 自动复制字段、目标端等价类型和同步键；二级索引、外键、触发器、分区、字段注释及数据库特有默认表达式不保证自动复制，需在创建确认页明确展示
- **目标表已存在**：任务创建阶段不主动修改结构，仅在以下条件全部满足时允许写入：所有必需源字段均有兼容目标列、同步键一致、目标额外列允许为空或具有默认值、类型转换不会明显丢失精度。缺列、键冲突、长度/精度不足时终止创建并报错；目标表存在外键、触发器或额外唯一约束时给出风险提示，因为它们可能改变数据或导致写入失败
- 运行期间的结构变更按第 5 节规则单独处理，不受“创建阶段不改已有表结构”规则限制
- **复合主键支持**：binlog 增量同步、断点续传、无主键检查等机制均需支持**联合主键**（多列组合主键），设计与开发时不能假设主键只有一列
- **大字段类型（TEXT/BLOB/JSON）**：跟随第 1 节的类型映射策略处理；创建任务时估算大字段占比并提示风险，同步速率同时按行数和字节数限制，避免“行数不高但单行过大”拖垮源库
- **字符集处理**：自动检测源表字符集，目标端使用等价的完整 Unicode 编码/字段类型（例如 MySQL `utf8mb4`、PostgreSQL `UTF8`、SQL Server Unicode 字符类型），不能把 `utf8mb4` 作为所有目标库的统一配置名；旧编码必须按源端真实字符集解码并提示潜在乱码风险
- **日期时间处理**：明确配置源端时区；MySQL `TIMESTAMP` 按时间点语义转换，`DATETIME` 按无时区本地时间保留。零日期、超出目标范围的日期和精度损失默认阻断任务，由用户处理数据或明确选择兼容策略
- **源库保护 / 读取限速**：同步任务支持配置最大行数/秒、最大字节数/秒、快照并行度和连接池上限，默认采用保守值，避免全量同步大表时占满源库 IO/连接资源
- **删除任务的数据处理原则**：删除任务默认停止同步进程、清理活动任务配置，并通过引擎清理该任务对应的 checkpoint/savepoint；不删除目标端已同步数据。操作审计和任务运行摘要按保留策略留存；如需清空目标数据，应作为需要二次确认的独立高危操作，不与“删除任务”绑定

### 9. 任务创建向导——分步设计决策
五步流程（数据源 → 同步粒度 → 目标端 → 字段映射 → 同步方式）逐步细化如下：

**第一步·数据源**
- 选择已注册数据源时，做一次**轻量重新连接检测**（而非完全信任上次测试结果），避免密码变更/网络问题导致任务创建后才发现连不上
- 选定数据源后自动探查库内的库/表列表，为下一步做准备；选择增量相关模式时同步执行第 1 节的 CDC 前置检查

**第二步·同步粒度**（基础规则见第 2 节）
- 多表模式：表数量可能很多，列表需支持**搜索/筛选**
- 单表模式：作为可选高级项，支持排除非同步键字段（如大文本/敏感字段），同步键字段不可排除
- 简单行过滤会引入 CDC 条件进出、目标端补写/删除等额外语义，不纳入 MVP，后续作为独立的数据选择能力设计

**第三步·目标端**
- 关系型目标：选择目标数据库/schema，表名默认与源表同名并支持改名；检测目标表是否存在并按第 8 节执行兼容性校验
- 全量或全量+增量任务在此选择目标数据处理模式，并展示 upsert、覆盖刷新、目标删除传播等实际效果
- **Kafka 目标**：主题名默认自动生成为"库名_表名"，分区策略默认按主键哈希（保证同一行多次变更的顺序性）；用户无需理解底层机制，用默认值即可运行，需要时可自定义
- **Redis 目标**：默认以"表名:主键值"作为 key，每行数据存为一个 Hash 结构，同样提供默认规则、非强制理解

**第四步·字段映射**（策略见第 1 节）
- 界面以"源字段→目标字段→类型"对照表呈现，自动匹配的字段默认隐藏细节，仅高亮有歧义需确认的字段
- 同步到 Kafka/Redis 等非关系型目标时，此步骤按目标端默认数据模型简化，仅保留必要的 key/分区规则与“排除字段”选项，不强制用户理解逐字段类型映射

**第五步·同步方式**
- 若源表在第二步未找到可靠同步键，此步“增量”和“全量+增量”选项直接置灰并提示原因，而非选中后才报错
- 全量同步默认"创建后立即执行一次"，支持改为定时执行（如每日定时全量刷新）
- 纯增量同步必须选择启动位点策略并确认目标端已经具备可信历史基线
- 同步速率上限（见第 8 节）作为本步的高级选项，默认给保守值
- **末屏为汇总确认页**：展示前五步全部已选内容、预检查结果、风险提示、任务名称/备注输入框，确认无误后提交，避免中途遗忘前序选择

## 五、非功能性需求与验收口径

- **部署环境**：支持内网/离网部署；SeaTunnel、JDBC 驱动、前后端依赖和容器镜像必须形成可离线安装包，不在运行时从公网下载组件
- **单机可靠性**：MVP 不承诺节点级高可用，但平台元数据库、SeaTunnel checkpoint 目录和加密主密钥必须位于可持久化、可备份的位置；进程重启后应能恢复任务状态
- **可扩展性**：连接器配置、类型映射、目标端能力和 DDL 策略按数据源类型注册，避免在业务流程中硬编码 PostgreSQL；未来新增目标端时不重写任务主流程
- **一致性口径**：MVP 默认采用“至少一次传输 + 基于同步键的幂等 upsert/delete”，保证最终目标表不产生重复主键且能收敛到源端状态。若目标库和部署环境满足 XA 条件，可通过 POC 评估严格 exactly-once，但不作为所有目标端的统一承诺
- **事务边界**：保证同一同步键的变更按顺序应用；MVP 不承诺一个源端事务涉及多表时在目标端原子可见，多表之间采用最终一致性
- **性能与容量**：以单表千万级为必须覆盖场景；任务最大表数、最大总数据量、快照吞吐、CDC 峰值吞吐、允许延迟、允许源库负载增幅和恢复时间目标由 Phase 0 基准测试确定并写入兼容矩阵
- **恢复边界**：正常进程异常应从最近成功 checkpoint 恢复；checkpoint 损坏或 binlog 已过期时必须进入“需重新初始化”，不得跳过缺口后继续运行
- **可观测性**：平台状态与 SeaTunnel 引擎状态定期对账；平台重启后能够重新发现仍在运行、已失败或已完成的引擎作业，避免出现“平台显示停止但引擎仍在写入”的失联任务

## 六、技术架构选型

结合前面的评估结论——SeaTunnel 适合作为底层同步执行引擎，但不提供面向非 DBA 用户的管理界面——整体采用 **B/S 架构**。本质上这个平台是一个"管理平台"（用户登录、权限、菜单导航、数据 CRUD、操作日志 + 同步业务模块），因此决定**基于开源脚手架 RuoYi-Vue-Plus 二次开发**，而不是从零搭建通用管理能力：

```
浏览器（Web 界面）
      │  HTTP
      ▼
前端：React 19 + TypeScript + Ant Design（基于 RuoYi-Vue-Plus 官方 **plus-ui-react** 前端二次开发）
      │  REST API
      ▼
后端：Spring Boot + Sa-Token + MyBatis-Plus（基于 RuoYi-Vue-Plus 后端脚手架二次开发）
      │  ├─ 脚手架自带：用户/角色/菜单权限、操作日志、登录日志
      │  ├─ 自研业务模块：数据源管理、同步任务管理、主键检查、类型映射提示、凭证加密存储
      │  ├─ 自有元数据库（MySQL）：任务配置、表实例、引擎 jobId、checkpoint 元数据、审计日志
      │  └─ SeaTunnel 作业管理适配器：REST API + savepoint/restore 控制能力
      ▼
SeaTunnel Zeta 引擎（单机模式起步，架构上可平滑演进到集群模式）
      │  ├─ 持久化 checkpoint/savepoint 存储
      │  └─ MySQL 源端 / PostgreSQL 目标端（MVP）
      ▼
后续扩展目标端：Oracle・SQLServer・Kafka・Redis・MongoDB・ES
```

**选型理由**：

- **后端选 Spring Boot（Java）**：SeaTunnel 本身是 Java 生态。以 SeaTunnel 2.3.13 作为 Phase 0 评估基线，REST API v2 提供作业提交（`POST /submit-job`、`POST /submit-job/upload`、`POST /submit-jobs`）、停止、状态、日志和 checkpoint 监控；暂停/恢复通过官方 savepoint/restore 能力接入。后端使用统一适配器屏蔽 REST 与任务控制方式的差异，POC 后固定准确版本和调用方式
- **前端选官方 plus-ui-react 版**（RuoYi-Vue-Plus 6.X 官方新增的 React 前端，技术栈为 React 19 + TypeScript + Ant Design + Umi Max + Vite）：Ant Design 的视觉调性偏"企业级、信息密度高、专业感强"，与你倾向的 Vben Admin 风格是同一路数，能达到类似阿里云 DTS 那种"任务列表+监控图表"的专业观感；相比社区组合（如 ruoyi-plus-vben5），官方版本与后端接口/权限体系的适配是官方维护、保持同步的，长期兼容性和可持续性更有保障，代价是生态积累时间较短（6.X 才新增），配套资料和社区案例会少于 Vue + Element Plus 版本
- **复用脚手架：dromara/RuoYi-Vue-Plus**（而非原版 RuoYi-Vue3）：技术栈是 SpringBoot + **Sa-Token**（权限认证，支持注解式校验和 AND/OR 复杂权限表达式） + **MyBatis-Plus**（对象化操作、基本免手写 SQL，插件丰富），同样自带用户管理、角色权限（含按钮级）、菜单管理、字典管理、操作日志、登录日志、在线用户监控等能力
  - 相比原版优势：MyBatis-Plus 大幅减少业务表（数据源管理、同步任务管理）的手写 SQL 工作量；原生支持 MySQL/Oracle/PostgreSQL/SQLServer 异构切换，技术栈跟同步目标端天然契合；用 Redisson 操作 Redis，为后续任务并发控制（如防止同一同步任务被重复触发）打好基础
  - 需要注意的取舍：**v6.0.0 版本起已整体移除多租户功能**，跟你们单组织内部工具的场景刚好契合，不用再考虑精简；但同版本也不兼容升级到了 SpringBoot 4.X 全系列、JDK 21，部署环境的 JDK 版本要对齐；相比原版**必须依赖 Redis**（用于缓存/Session），部署环境要多装一个 Redis 服务，不算难事但要提前规划
  - **选单体形态而非分布式集群形态**：当前定位是单机部署，暂不需要该脚手架面向的"分布式集群"重型能力，等真正需要时再评估升级路径
- **平台自身的元数据库直接复用 MySQL**：你已经熟悉 MySQL，RuoYi 默认也是 MySQL，不需要为了"存任务配置"这件事再引入一个陌生的数据库

**关键集成点（决定"自己要写多少代码"的地方）**：

| 平台职责（自己开发） | RuoYi-Vue-Plus / plus-ui-react 脚手架职责（直接复用） | SeaTunnel 职责（直接调用） |
|---|---|---|
| 数据源管理、任务创建向导、字段映射提示、主键检查 | 用户/角色/菜单权限、登录鉴权（Sa-Token） | 实际的数据读取/写入/CDC 捕获 |
| 保存任务/表实例/jobId/配置版本/checkpoint 元数据，不保存或伪造引擎状态 | 操作日志、登录日志 | checkpoint/savepoint 内容、实际 binlog 位点和故障恢复 |
| 通过作业管理适配器提交、暂停、恢复、停止任务，并把引擎状态翻译成平台状态 | 通用业务表 CRUD（借助 MyBatis-Plus 减少手写 SQL） | 任务运行时的调度、容错、重试和指标输出 |
| 凭证加密存储、同步业务规则 | | 无（SeaTunnel 不管这块） |

## 七、阶段划分建议

| 阶段 | 内容 |
|---|---|
| Phase 0 | SeaTunnel 2.3.13 基线 POC；锁定 MySQL/PostgreSQL 版本矩阵、checkpoint/savepoint、REST/任务控制适配、全量+增量一致性、upsert/delete、DDL 和性能基线 |
| Phase 1（MVP） | MySQL → PostgreSQL；支持全量、binlog CDC 增量、全量+增量、整库/多表/单表、断点恢复、基础监控与数据核对 |
| Phase 1.1 | 扩展 Oracle、SQL Server 等关系型目标，并为每种目标建立独立类型映射和能力矩阵 |
| Phase 2 | 扩展 Kafka、Redis、MongoDB、Elasticsearch 等非关系型目标，适配消息格式、主键/key 和删除事件语义 |
| Phase 3 | 完善主动告警、自动 DDL 支持范围、在线数据校验和多用户并发治理 |

（此前在 GoldenDB → Kafka 上做的技术验证，可以视为 Phase 2 的提前预研，不影响当前 MVP 范围的定义）

### MVP 核心验收场景

| 场景 | 必须达到的结果 |
|---|---|
| 全量期间源表持续发生增删改 | 全量完成后连续进入 CDC，无人工切换窗口，最终目标状态与源端一致 |
| 单主键、联合主键、非空唯一键 | INSERT/UPDATE/DELETE 均正确落到目标端，不产生重复主键 |
| 无可靠同步键 | 只能创建全量任务，增量相关选项不可用 |
| 引擎或平台进程重启 | 从最近成功 checkpoint 恢复，不重新执行已完成的全量 |
| 暂停后恢复 | savepoint 成功后进入已暂停，使用相同配置版本恢复并继续处理后续变更 |
| 目标库短暂不可用 | 自动重试；恢复后最终数据收敛，超过重试策略则进入失败可恢复状态 |
| binlog 已过期或 checkpoint 损坏 | 明确进入需重新初始化状态，不从最新位点静默跳过缺失数据 |
| 目标表已存在 | 兼容结构允许同步；缺列、同步键冲突或精度不足时在提交前阻断 |
| 新增字段与高风险 DDL | 仅支持矩阵内的安全新增字段自动处理；其余变更暂停受影响表并提示原因 |
| 整库任务发现新表 | 新表独立完成检查和历史全量后进入 CDC，不影响其他正常表 |
| TEXT/BLOB/JSON、emoji、旧编码、日期时间边界值 | 按映射规则正确同步；无法无损处理的数据在提交或运行前明确阻断 |
| 周期全量执行失败 | 不得把半成品数据标记为成功；覆盖刷新模式应保留原可用目标数据或明确处于维护状态 |

## 八、需求确认结论（v0.3）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 使用者是谁 | 技术背景但非 DBA，要求操作简单；先支持单用户，后续扩展多用户并发使用 |
| 2 | 目标端优先级 | MVP 首先完整支持 PostgreSQL；之后扩展 Oracle/SQL Server，再扩展非关系型目标 |
| 3 | 同步方式 | 全量、增量、全量+增量三种都要支持；MySQL 源端增量走 **binlog（需 ROW 模式）** |
| 4 | 源端范围 | 短期仅 MySQL，暂不支持 GoldenDB 等其他源 |
| 5 | 数据量级 | 以中小表为主，个别单表可达千万级，需要成熟稳健的底层引擎 |
| 6 | 部署形态 | 先单机部署，暂不做高可用，但架构设计上不堵死未来集群化的路 |
| 7 | 表结构变更处理 | 仅支持矩阵内且预检查通过的安全新增字段自动处理；其他新增字段及高风险变更暂停受影响表，人工确认后继续 |
| 8 | 同步粒度 | 需支持整库 / 多表 / 单表三级粒度；场景是纯数据复制，任务间无依赖顺序，暂不需要任务编排 |
| 9 | 同步键规则 | 优先源表主键；无主键时仅接受全部列为 NOT NULL 的唯一索引；无可靠同步键只能走全量同步 |
| 10 | 跨数据库类型转换 | 常规类型自动映射，有歧义类型提示确认；Kafka 使用标准 JSON CDC 事件，Redis 使用 Hash 模型，时间统一采用 ISO 8601 表达 |
| 11 | 断点续传机制 | SeaTunnel 持久化 checkpoint/savepoint 是恢复权威来源；平台只保存关联和展示元数据；GTID 为推荐源端能力但不是唯一恢复机制 |
| 12 | 凭证存储方案 | 平台内加密存储，主密钥与数据库分离；源/目标账号分权；SeaTunnel 配置和日志不得泄露明文凭证 |
| 13 | 告警渠道 | 不纳入 MVP，MVP 阶段仅需监控界面可见状态，主动推送告警放到后续阶段 |
| 14 | 整库同步新表处理 | 默认自动纳入新表；新表同样需过主键检查，已有历史数据的新表先全量再切增量；新表发现靠定期扫描（间隔可配置） |
| 15 | 技术架构 | B/S 架构；前端 React 19 + TypeScript + Ant Design，后端 Spring Boot + Sa-Token + MyBatis-Plus；通过 SeaTunnel 作业管理适配器整合 REST API 与 savepoint/restore；平台元数据库用 MySQL，并部署 Redis |
| 16 | 开发优先级 | 先实现核心功能（任务创建、全量/增量同步、监控可见状态），次要功能（告警、多用户权限体系等）后置 |
| 17 | 脚手架选型 | 基于开源脚手架 **dromara/RuoYi-Vue-Plus v6.0.0+**（Sa-Token + MyBatis-Plus + Redisson，单体形态，SpringBoot 4.X / JDK 21）二次开发，前端采用官方 **plus-ui-react**（React 19 + Ant Design，信息密度高、观感专业，区别于若依默认经典风格）；该版本已整体移除多租户功能，契合单组织场景；需额外部署 Redis |
| 18 | 目标表冲突处理 | 不存在则自动创建字段和同步键；已存在时执行字段、类型、同步键和额外列兼容性检查，不兼容则提交前阻断 |
| 19 | 复合主键支持 | binlog 增量、断点续传、主键检查等机制均需支持联合主键，不假设主键只有一列 |
| 20 | 字符集与时间处理 | 自动检测源字符集，目标使用等价 Unicode 编码/类型；显式处理时区、TIMESTAMP/DATETIME、零日期和精度边界 |
| 21 | 源库保护 | 支持行数/秒、字节数/秒、快照并行度和连接池上限，避免全量同步拖垮生产源库 |
| 22 | 删除任务的数据处理 | 删除任务会停止作业并清理平台记录及对应引擎恢复状态，但不删除目标数据；清空目标数据是独立高危操作 |
| 23 | 一致性语义 | 默认至少一次传输 + 同步键幂等 upsert/delete，保证关系型目标最终状态收敛；严格 XA exactly-once 仅按目标库能力评估 |
| 24 | 增删改语义 | 源端 INSERT/UPDATE 写入目标最新状态，DELETE 默认在目标硬删除；目标表默认由同步任务独占写入 |
| 25 | 任务生命周期 | 暂停保留 savepoint，恢复沿用相同配置版本；停止不承诺可恢复；失败重试与重新初始化是两个独立操作 |
| 26 | 全量目标数据处理 | 全量写入已有目标表时必须选择合并 upsert 或覆盖刷新；前者不删除目标多余数据、不承诺严格镜像，后者不得以半成品替换成功数据 |
| 27 | 字段与行过滤 | MVP 仅允许排除非同步键字段；行过滤后置，避免在未定义 CDC 条件进出语义前引入数据错误 |
| 28 | 配置版本 | 已发布配置不可原地覆盖；影响同步语义的修改生成新版本，checkpoint 只能由产生它的配置版本恢复 |
| 29 | 跨表事务 | 同一同步键的事件保持顺序；MVP 不承诺源端跨表事务在目标端原子可见，多表之间最终一致 |

## 九、下一步：Phase 0 技术验证

在大规模开发管理界面前，先完成一条最小但完整的 MySQL → PostgreSQL 技术闭环，用结果冻结以下内容：

1. **版本与环境**：确定 SeaTunnel、MySQL、PostgreSQL、JDBC 驱动和 JDK 的准确版本，制作离线依赖清单。
2. **核心链路**：验证单表及多表的全量、纯增量、全量+增量，覆盖 INSERT/UPDATE/DELETE、单主键、联合主键和非空唯一键。
3. **恢复能力**：验证 checkpoint 持久化、进程重启、暂停/savepoint、恢复、目标库暂时不可用、binlog 过期和重新初始化。
4. **目标端语义**：验证自动建表、已有表兼容检查、upsert、硬删除、字段类型映射、日期时间、字符集和大字段。
5. **变化处理**：验证新增字段、高风险 DDL、整库新增表发现及单表故障隔离；无法由 SeaTunnel 原生支持的能力明确由平台补齐或从 MVP 降级。
6. **性能基线**：使用接近生产的数据分布测试千万级表，记录快照吞吐、CDC 峰值吞吐、延迟、源库负载、checkpoint 大小和恢复时间。
7. **接口适配**：验证 REST 提交/监控/停止与 savepoint/restore 的组合，形成稳定的 SeaTunnel 作业管理适配接口。

Phase 0 必须输出：技术验证报告、支持版本矩阵、MySQL→PostgreSQL 类型映射表、异常恢复矩阵、性能基线、SeaTunnel 作业管理接口约定。核心恢复与一致性场景未通过前，不进入完整 MVP 页面和业务模块开发。
