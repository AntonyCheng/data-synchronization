# 多表同步设计

## 目标与边界

MVP 支持显式多表任务组和整库范围任务组。两者均支持 MySQL -> PostgreSQL/MySQL/Kafka、全量 + binlog CDC；整库组可选择自动发现新增表。执行模型仍是一张表一个 SeaTunnel job，不引入跨表事务或自动 DDL。

表项的字段选择在保存时物化为具体列并同时记录源表结构基线；启动和“重新初始化该表”时，覆盖了基线全部列的选择被视为“整表”，会按源表当前结构重新推导（新增列自动纳入，并在启动前校验中一并检查目标端），显式子集则原样保留。新发现的表沿用组内已有表项的目标 schema，没有时取目标数据源配置的 schema（PostgreSQL 默认 `public`）。

## 任务组与映射

- `ds_sync_task_group` 表示一次可编排的同步发布，拥有独立版本、状态和创建人。
- `ds_sync_task_group_item` 表示表级映射：源库/表、目标 schema/表、主键列、列映射 JSON、DDL 策略和表级状态。
- 发布生成配置版本；编辑会递增 `config_version`，运行中的版本只读。当前 MVP 的执行适配器为“任务组内每张表一个 SeaTunnel job”：表项的 `engine_job_id`、配置指纹和生命周期是权威数据，组级字段只保存聚合摘要。这样可以隔离单表失败并支持逐表暂停/恢复，后续具备统一多表 source/sink 能力后再评估合并为单 job。
- 源表引用必须使用白名单数据源，并在发布前重新读取元数据，拒绝不存在或结构不兼容的表。

## 数据与键约束

- 每张表必须有主键；没有主键时仅允许明确配置的全局唯一且所有列非空的唯一键。
- 复合键按列顺序保存，不能依赖数据库返回顺序；目标端必须存在同等唯一约束。
- 列映射必须显式处理名称冲突、保留字、精度/时区和不可转换类型，禁止静默截断。
- 目标表 DDL 策略分为 `REQUIRE_EXISTING`、`CREATE_IF_MISSING`、`MANUAL_MIGRATION`；字段新增、删除、类型变更默认阻断发布并给出表级差异。

## 作业与故障模型

- 每个表项生成一份独立的 MySQL -> PostgreSQL 配置并提交一个 SeaTunnel job；每个 job 拥有独立 checkpoint/savepoint。组级操作按表项顺序执行并聚合结果，不把组级状态误当成单表状态。
- 显式多表组保持原子启动：任一表校验或提交失败时补偿停止前序作业。整库组将发现阶段已确认的表级错误隔离为 `FAILED`，继续提交其他可用表；运行中新增表提交失败也只影响该表，组状态聚合为 `DEGRADED`。
- 任务组状态为 `DRAFT -> VALIDATING -> RUNNING/DEGRADED -> PAUSING -> PAUSED/FAILED -> STOPPED`，表项另存 `PENDING/RUNNING/DEGRADED/FAILED/FINISHED`。显式多表启动失败时已提交的前序表项会被停止并记录补偿错误，避免出现“接口失败但部分运行”的隐性状态。
- 恢复使用同一版本配置和 job 级 savepoint；若映射、列或凭证版本变化，必须新建版本并重新全量。

### 部分失败语义（生命周期不使用数据库事务）

组级生命周期（启动 / 发现 / 暂停 / 恢复 / 停止 / 刷新 / 逐表恢复 / 逐表重新初始化）以及 DDL 检查**刻意不包在数据库事务里**：它们沿途调用引擎，而回滚撤销不了已提交或已停止的作业——在事务里中途失败，库里会回到一个引擎已经不在的状态；事务还会在串行 REST 调用期间一直占着连接和行锁，并且组锁在方法体返回时就释放、事务却在其后才提交，另一实例可能拿到锁读到未提交的行。现在的规则是：每次落库各自提交，**所有拒绝都在第一次引擎调用之前判定**，引擎中途失败时留下诚实的逐表结果：

| 操作 | 某张表在引擎侧失败时 |
|---|---|
| 启动（显式多表） | 补偿停止已提交的前序作业，组 `FAILED`（原子语义不变） |
| 启动 / 发现（整库） | 该表隔离为 `FAILED`，其余继续，组 `DEGRADED` |
| 暂停 | 该表 `FAILED` 并记录原因、保留 job id；其余继续做 savepoint，组保持 `PAUSING` 由状态刷新收敛 |
| 恢复 | 配置指纹等拒绝条件先对全部表判定完再提交；某表被引擎拒绝则该表 `FAILED`（savepoint 保留，可「恢复该表」重试），已恢复的表继续运行，组聚合为 `DEGRADED` |
| 停止 | 跳过已 `STOPPED`/`FINISHED` 的表；某表停止失败则 `FAILED` 并保留 job id，其余照常停止，组 `FAILED`，可直接重试停止 |
| 逐表恢复 | 新基线在提交前读取，读失败不会留下「作业在跑、表项仍是阻塞」 |
| 逐表重新初始化 | 目标兼容性等校验在销毁旧作业之前完成（被拒绝时旧作业与 savepoint 原样保留）；新作业提交失败时表项解除旧 job id、置 `FAILED`，可直接重试 |

编辑与删除只动数据库，使用事务，但**事务在组锁之内**（先加锁、再开事务、提交后才释放锁），避免与并发启动交错——否则启动可能为已被删除的表项提交出无主作业。单表任务的编辑与删除同理使用任务锁。

### 整库任务组的保存：先规划、后落库

保存（新建或编辑）整库组要做远程工作：列出源库的表、逐表读取结构、推导字段选择与结构基线、校验同步键与目标兼容性，Kafka 目标还要逐表建 topic。这些全部在**打开数据库事务之前**完成（`ISyncTaskGroupDiscoveryService.plan` / `readmitRejected`，只读外部系统、不写库）；随后一个事务只写入规划好的组行与表项行。编辑时整个过程都在组锁内：先加锁、规划、再开事务写入、提交后释放锁。

- 规划本身失败（源库不可达、列不出表、请求自带的表读不到结构）时拒绝保存，**什么都不写**——与过去事务回滚的用户可见效果相同，只是事务不再在远程调用期间占着连接。
- 单张表读取或校验失败不拒绝保存：该表以 `FAILED` 写入并记录原因，与发现一致。
- 规划阶段已创建的 Kafka topic 不会因为保存被拒而删除；建 topic 幂等，下次保存或启动直接沿用。
- 组只在 `DRAFT` / `STOPPED` 时可编辑，表项都没有在跑的作业，所以保存从不调用引擎。

编辑整库组时表项的去留：

| 编辑内容 | 表项 |
|---|---|
| 源数据源、源库、目标数据源都没变（例如只改名称、限速、自动发现） | **保留**全部已有表项：id、目标 schema、指标历史、DDL 事件记录与表级状态均不变，已有表不重新读取；只为源库中新增的表补充表项，仍受 `sync.group.max-tables` 约束（只补到上限，其余在组错误信息中说明）；表项 DDL 策略跟随组 |
| 同上，且某表在运行之前就被拒（`FAILED` 且没有引擎作业：无可用同步键、目标不兼容、topic 缺失、提交被拒） | 按发现规则重新校验（Kafka 目标先补建 topic，整表选择跟随源表当前字段）；通过则回到 `PENDING` 并刷新结构基线，下次启动即提交；仍不通过则保持 `FAILED` 并更新为当前原因。整库启动会跳过 `FAILED` 表，过去是编辑时的整体重建让它们有机会重试 |
| 源数据源、源库或目标数据源任一变化，或由多表组改为整库组 | **重建**：原表项属于旧端点，连同其 DDL 事件一起删除，按新端点重新发现全部表 |
| 请求自带表项列表（向导不会为整库组发送） | 按请求重建这些表项（同多表组），再发现其余表 |

一次保存只递增一次 `config_version`（过去整库组保存时内部调用的发现还会再递增一次）。保存后组的错误信息记录校验未通过的表数和因上限未纳入的表数。显式多表组的保存不变：请求中的表项整体替换原表项，在保存事务内读取表结构。

发现新增表（手动 `discover`、自动发现周期、保存时补充表项）**不递增** `config_version`：新增一张表不改变任何已有表的配置，而版本号是每个 Kafka 表项 raw topic 名（`__ds_raw_{itemId}_v{version}`）和配置指纹的一部分。过去运行中的发现会递增版本，后果是后端重启后桥接改读新名字的空 topic、数据静默停发，暂停的 Kafka 表也无法恢复（2026-09-25 修复前实测：运行中发现一张新表后暂停再恢复，原有表和新表均被拒绝，要求重新初始化）。`config_version` 只随编辑递增，而编辑要求组已停止。

**整库组的源库**可以不是数据源配置的默认库（向导第 1 步「源数据库」）。每个表项记录自己的 `sourceDatabase`，引擎作业的一切（MySQL-CDC 的库过滤与表名、JDBC 连接、主键与字段读取、`FULL` 预建 MySQL 目标时的 `SHOW CREATE TABLE`、Kafka 桥接的快照行）、目标兼容性检查和行数核对都在表项的库中进行（`SyncTaskGroupConfigGenerator.itemSource`）；表项在默认库时生成的配置与指纹逐字不变。修复前引擎作业一律读默认库：默认库没有同名表时启动失败（“源表没有可同步字段”），有同名表时同步的是默认库的那张表。

## 校验、审计与资源

- 全量完成后按表记录源/目标行数、差异数量和最近检查结论；组级结果是所有表结果的汇总，不掩盖失败表。当前已实现只读 `COUNT(*)` 逐表核对；单表数值同步键支持 `KEY_RANGE` 分块核对并返回块级统计，联合键/字符串键回退 `COUNT`，共同 CDC 水位校验仍为后续能力。
- 记录发布人、版本、配置指纹、引擎 jobId、开始/结束时间和脱敏错误；明文密码只在运行时从解密实体进入配置，不落库到引擎配置。
- 每组表数上限由 `sync.group.max-tables` 配置（默认 20，取值 1..200）：多表保存时校验，整库自动发现也受约束（只补到上限，超出的表不纳入并在组的错误信息中说明）；每张表是一个独立作业、各占一条到源库的 binlog 连接，上调前先评估源库。每个数据源 2 个并行组；并发、checkpoint 间隔、读取速率按组配置并做上限校验。
- 大表与高频表应拆分任务组，避免单一 checkpoint 状态和反压影响无关表。

## 分阶段实施

1. 元数据表与版本 API：组、表项、发布校验和差异预览（已实现）。
2. 多表配置生成：当前采用每表独立 job、配置脱敏和配置指纹（已实现）。
3. 表级状态与校验：组级聚合、逐表错误、整库新增表发现、失败表隔离和逐表行数核对结果持久化已实现；单表 `KEY_RANGE` 块级行数核对已实现，同步键抽样/逐行摘要和告警事件待后续。
4. 性能与兼容性：并发限制、旧单表任务迁移为单项任务组、灰度发布和回滚。
